## Blockers

### DCR-0005 — `weakness_classes` has no membership validation, letting a miscased class silently bypass the W2 seed_arm hard block

- **Severity:** high (adjudicated: exploitability 2 × impact 3 × exposure 1.0 = 6.0)
- **Standard:** logic (general correctness, no CWE mapping)
- **Location:** `src/mylonite/plugins/_mcp/target_file.py:87` in `TargetFile`
- **Reachable from:** `mylonite scan --target-file`, `mylonite gate --target-file`, `mylonite validate --target-file` — all target-file-driven entrypoints

**Failure scenario.** A `target.yaml` with `weakness_classes: ["w2"]` (lowercase, or any other typo of `W2`) and no `seed_arm` passes `TargetFile` validation — only `control_env` keys are checked against `_WEAKNESS_CLASSES`. `validate_for_scan`'s `set(tf.weakness_classes) & _INDIRECT_ONLY_WEAKNESS_CLASSES` intersection is then empty (case-sensitive), so the hard pre-flight block — which exists specifically to stop a seed-less W2 target from silently reading as clean — never fires, and the scan proceeds without ever planting the indirect-injection payload.

**Evidence.**
```python
weakness_classes: list[str] = []
```

**Proposed fix.** Add a validator in `TargetFile._check` (mirroring the existing `control_env`-key check already present in the same class) that rejects any `weakness_classes` entry not in `_WEAKNESS_CLASSES`.

**Proof test.** Not yet written — recommend `tests/plugins/test_target_file.py::test_weakness_classes_rejects_unknown_or_miscased_entry` asserting `TargetFile(weakness_classes=["w2"])` raises a `ValidationError`.

### DCR-0009 — `_is_secret_env` never checks the key name when the env value is non-string

- **Severity:** high (adjudicated: exploitability 2 × impact 3 × exposure 1.0 = 6.0)
- **Standard:** logic (general correctness, no CWE mapping) — directly material to T9's secret-handling scope
- **Location:** `src/mylonite/_redaction.py:374` in `_is_secret_env`
- **Reachable from:** `redact_target_yaml`, called from all three write sites in `cli.py` (scan scaffold, generate, gate-PR artefact write) — every path that persists a `target.yaml` copy

**Failure scenario.** `redact_target_yaml` on a `target.yaml` containing `env:\n  API_TOKEN: 8675309123456` (an unquoted numeric token — YAML parses this as a Python `int`, not `str`) hits `_is_secret_env`'s leading `isinstance(value, str)` check, which returns `False` *before* `_key_looks_secret(key)` is ever evaluated. The key name obviously signals a credential, but the raw numeric value is written verbatim into the persisted `.mylonite` target.yaml copy — exactly the file this release's `${VAR}` indirection work (T9) exists to make safe, and exactly the file the docs tell an operator to commit/push as a gate artefact. The sibling `headers` masking path is type-agnostic, confirming this is an asymmetry, not a deliberate design choice.

**Evidence.**
```python
    if not isinstance(value, str):
        return False
    if _key_looks_secret(key):
```

**Proposed fix.** Check `_key_looks_secret(key)` before the `isinstance(value, str)` short-circuit, or coerce `value` to `str` first so a key-name match still masks a numeric/boolean-typed secret.

**Proof test.** Not yet written — recommend extending `tests/test_redaction.py` with `test_numeric_valued_secret_key_is_still_masked` asserting `redact_target_yaml` on a YAML doc with `env: {API_TOKEN: 8675309123456}` produces no occurrence of `8675309123456` in the output.

**Escalated:** yes, adjudicated by opus → confirmed at high (up from the original reviewer's high, unchanged, but independently re-derived from the rubric rather than taken on trust).

## Cross-cutting themes

1. **`_redaction.py` has three independent gaps in the same release that adds `${VAR}` indirection to it (T9).** DCR-0009 (non-string value skips key-name check), DCR-0010 (unconditional masking doesn't recurse into lists/dicts), DCR-0014 (quoted-dict-repr bypasses the KV regex), and DCR-0015 (URL-embedded credentials never redacted in `redact_target_yaml`) are four distinct code paths in the same file that share one root pattern: the module's masking logic was built and tested against the "normal" case (a flat string value under a plain key) and doesn't yet cover the shapes that show up once you go looking for them (non-string YAML values, nested collections, dict reprs, URLs). Given `_redaction.py` is explicitly gated on maintainer sign-off this release, this cluster is worth reviewing together rather than one finding at a time — fixing DCR-0009 alone without the other three leaves the same "committed copy still leaks in shape X" story just moved to a different shape.
2. **`--target-file` combined with a non-`mcp:custom` positional `TARGET` silently overrides the positional argument, in both `scan()` (DCR-0001) and `gate()` (DCR-0003)** — the same gap exists at both call sites because both independently re-derive "did the operator mean `--target-file` or the positional" rather than sharing one resolution function. This is the same class of bug the whole 0.7.7 release exists to close (Class A: fail-opens from re-derived logic instead of a single source of truth) — it just wasn't in the plan's original defect list because it wasn't found until this review.
3. **`DifferentialValidator`'s live re-drive loops (DCR-0016 through DCR-0019) are all the same pattern repeated four times in one class**: N or 2N independent, statistically-uncorrelated LLM-driven scans run in a plain sequential Python `for`/list-append loop instead of a bounded `gather`. None are individually severe, but together they mean `mylonite validate --iterations 5` against a custom target with a guarded adapter costs roughly `5 + 5 + 7 = 17x` a single scan's wall-clock instead of something closer to `max_concurrent`-bounded — worth a single follow-up task consolidating all four into one concurrency-bounded runner rather than four separate point fixes.
