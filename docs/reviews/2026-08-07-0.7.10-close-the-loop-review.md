## Blockers

### DCR-0001 — Scope-required `--authorize` check vacuously passes when both `authorize` and `scope` are `None`

- **Severity:** critical (adjudicated: exploitability 3 × impact 2 × exposure 1.0 = 6.0 → high; CWE-863 is CWE Top-25 → mechanically bumped to critical)
- **Standard:** CWE-863 (Incorrect Authorization)
- **Location:** `src/mylonite/cli.py:949` in `_build_adapter_for_mcp`
- **Reachable from:** `mylonite scan mcp:<family>` (and `gate`/`validate`/`ablate` equivalents) for any family with `requires_scope=True`, run with no `:<scope>` segment and no `--authorize` flag

**Failure scenario.** Running `mylonite scan mcp:filesystem` (no `:<scope>` segment) with no `--authorize` flag makes `authorize != scope` evaluate `None != None` → `False`, so the explicit-authorization gate silently passes instead of rejecting the missing `--authorize`. Today the command is only stopped by an *unrelated* downstream validator — an empty-scope rejection specific to the `filesystem`/`github` families — not by this authorization check itself. A future `requires_scope=True` family whose validator tolerates an empty scope would let an operator launch it with zero `--authorize` input, bypassing the authorization gate entirely.

**Evidence.**
```python
    if spec.requires_scope:
        if authorize != scope:
```

**Proposed fix.** Require `scope is not None and authorize == scope` (or explicitly reject `scope is None` first) so the authorize gate itself enforces the invariant instead of depending on a downstream, unrelated validator to happen to catch the same case.

**Proof test.** None generated this pass. Recommend a `test_cli.py` case that calls `_build_adapter_for_mcp` (or drives `scan mcp:filesystem` end-to-end) with `authorize=None` and no scope segment against a hypothetical/stubbed `requires_scope=True` family whose validator does not itself reject an empty scope, asserting the authorize gate rejects it directly.

**Escalated:** yes — adjudicated, exploitability 3 × impact 2 × exposure 1.0 = 6.0 → high, then mechanically bumped to critical (CWE-863, CWE Top-25).

**DCR-0005 — Per-payload flakiness-pass semaphore is a fresh instance, not the shared cross-payload semaphore, so effective concurrency scales to `max_concurrent²` instead of `max_concurrent`**

- **Severity:** medium (adjudicated: exploitability 3 × impact 2 × exposure 0.35 = 2.1 → medium, cartography-limited exposure — `ScanEngine` is on the hot path of every real `scan`/`gate`/`validate`/`ablate` invocation)
- **Standard:** internal logic-review checklist (no CWE mapping)
- **Location:** `src/mylonite/scan/engine.py:737` in `ScanEngine._run_flakiness_passes`
- **Reachable from:** any `scan`/`gate`/`validate`/`ablate` run with `runs > 1` and `max_concurrent` set

**Failure scenario.** With `ScanConfig(max_concurrent=3, runs=3)` and ≥3 applicable payloads: `run()` builds one outer `Semaphore(3)` admitting up to 3 concurrent `_process_one` calls. Each of those, when `runs > 1`, calls `_run_flakiness_passes`, which constructs its **own** new `Semaphore(limit)` rather than reusing the outer one — so each of the 3 concurrently-processing payloads can itself fan out up to 3 concurrent `adapter.invoke()` calls, yielding up to 9 simultaneous calls in flight against the target, 3× the configured cap. Confirmed independently by both the logic and performance specialist reviewers on separate passes.

**Evidence.**
```python
        limit = max(1, self._config.max_concurrent)
        sem = asyncio.Semaphore(limit)
```

**Proposed fix.** Thread the outer semaphore from `run()`/`_process_one` down through `_run_payload` into `_run_flakiness_passes` instead of constructing a new local one, so total in-flight `adapter.invoke()` calls never exceed `max_concurrent` regardless of `runs`.

**Proof test.** None generated this pass. Recommend a test that instruments `adapter.invoke()` to track peak concurrent in-flight calls under `max_concurrent=N, runs=M` with enough payloads to saturate both, asserting peak concurrency never exceeds `N`.

**Escalated:** yes — adjudicated, exploitability 3 × impact 2 × exposure 0.35 = 2.1 → medium. This is a real, independently-double-confirmed correctness bug in a load-bearing safety knob: operators set `max_concurrent` specifically to avoid overloading rate-limited or subprocess-backed targets.

## Cross-cutting themes

1. **Two critical, unrelated findings, not a repeated pattern this time.** Unlike 0.7.9's single dominant redaction-gap theme, this release's two critical findings (DCR-0001, the auth-bypass at `cli.py:949`; DCR-0002, the credential-in-URL leak at `cli.py:3418`) are independent root causes in independent code paths — one an authorization-logic gate, the other a missing redaction pass on a new scaffold field. Stating this plainly rather than forcing a false unifying narrative.

2. **The 0.7.9 redaction-gap fix is holding up well.** Of the ~7 redaction-gap locations fixed in 0.7.9 (DCR-0002/0003/0006/0016/0017/0022/0023 in that report), only one new instance surfaced this release (DCR-0002 here, the REST-scaffold credential-in-URL critical), and one apparent regression (DCR-0014, the stale `cli.py` comment) turned out to be documentation drift, not a real gap, on direct verification. This is a good signal that the 0.7.9 fix pattern is durable, not that the problem is spreading.
